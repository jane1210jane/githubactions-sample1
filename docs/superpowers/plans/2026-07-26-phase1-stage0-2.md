# フェーズ1（Stage 0–2）実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** GitHub Actions 未経験者が「最小のワークフロー → Python CLI の CI → PR ゲート」を順に体験できる教材リポジトリのフェーズ1を構築する。

**Architecture:** 積み上げ型。1 つの題材アプリ `sales-report`（売上 CSV の月次集計）を育てながら、`.github/workflows/` を段階的に追加・改修する。集計ロジックは副作用のない純粋関数として `src/sales_report/aggregate.py` に置き、CLI はその薄いラッパーにする。各ステージ完了時に `git tag stage-NN` を打ち、解説を `docs/stages/` に 8 節フォーマットで残す。

**Tech Stack:** Python 3.12 / uv / pytest / pytest-cov / ruff / GitHub Actions（`ubuntu-latest`）

## Global Constraints

以下は全タスクの要件に暗黙的に含まれる。

- Python は `>=3.12`。CI のランナーは `ubuntu-latest`。
- 依存管理は `uv` のみ。`pip install` を直接使う手順は書かない。`uv.lock` は必ずコミットする。
- すべてのワークフローに `permissions: contents: read` をトップレベルで書く。**理由の解説は Stage 6 まで行わない**（設計書の伏線方針）。ただし「Stage 6 で回収する」というコメントは残す。
- `run:` の中に `${{ }}` を直接書かない。外部から来る値は必ず `env:` を経由させる。これも理由の解説は Stage 6 で行う。
- アクションはメジャーバージョンタグで参照する（例 `actions/checkout@v5`）。SHA ピン留めは Stage 6 の学習対象なので**フェーズ1では行わない**。
- 解説ドキュメントは必ず 8 節フォーマット（ゴール / 前提 / なぜ必要か / 手順 / 何が変わったか / つまずきポイント / 演習課題 / 実務への持ち込みメモ）に従う。
- ドキュメント本文は日本語。コード中の識別子は英語。
- カバレッジは 80% 以上を維持する。ただし**フェーズ1では CI のゲートにしない**（Stage 4 の学習対象のため）。`--cov-fail-under` はまだ書かない。
- Stage 0–1（Task 1〜5）は `main` へ直接コミットする。Stage 2（Task 6）は `stage/02-triggers` ブランチ → PR → マージで進める。
- 金額は `Decimal` で扱う。`float` を使わない。
- データ構造は `frozen=True` の dataclass と `tuple` を使い、入力を破壊しない。

- [ ] **Step 1: hello.yml を作成する**

`.github/workflows/hello.yml`:

```yaml
# Stage 0: いちばん小さなワークフロー。
# 目的は「動かして、ログを読んで、ランナーの正体を知る」こと。
name: Stage 0 - Hello Actions

# on: どのイベントでこのワークフローを起動するか。
on:
  # push: どのブランチに push しても起動する（Stage 2 で絞り込む）
  push:
  # workflow_dispatch: Actions タブから手動で起動できるようにする
  workflow_dispatch:
    inputs:
      greeting_target:
        description: 挨拶する相手
        required: false
        default: world
        type: string

# permissions: このワークフローが GITHUB_TOKEN に許す操作。
# 最小権限にしておく。なぜ必要かは Stage 6 で回収する。
permissions:
  contents: read

jobs:
  greet:
    name: 挨拶してランナーを観察する
    runs-on: ubuntu-latest
    steps:
      - name: 挨拶する
        # 外部から来る値は run: に直接埋め込まず env: を経由させる。
        # 理由は Stage 6 で回収する。
        env:
          GREETING_TARGET: ${{ inputs.greeting_target || 'world' }}
        run: echo "Hello, ${GREETING_TARGET}!"

      - name: ランナーの素性を確認する
        run: |
          echo "----- OS -----"
          uname -a
          echo "----- 作業ディレクトリ -----"
          pwd
          echo "----- 作業ディレクトリの中身 -----"
          ls -la
          echo "（リポジトリのファイルが無いことに注目。取得は Stage 1 で行う）"

      - name: 証拠ファイルを作る
        run: |
          date --iso-8601=seconds > evidence.txt
          cat evidence.txt

      - name: 同じジョブの中ではファイルが残っていることを確認する
        run: cat evidence.txt

  check-isolation:
    name: 別ジョブから同じファイルを探す
    runs-on: ubuntu-latest
    # needs: greet ジョブの完了を待つ
    needs: greet
    steps:
      - name: 別ジョブに evidence.txt が存在しないことを確認する
        run: |
          if [ -f evidence.txt ]; then
            echo "見つかってしまった（想定外）"
            exit 1
          fi
          echo "存在しない。ジョブごとにランナーは別のマシンである。"
```

- [ ] **Step 5: Stage 0 の解説を書く**

`docs/stages/stage-00-first-workflow.md` を 8 節フォーマットで作成する。各節に必ず含める内容:

1. **このステージのゴール** — ワークフローを 1 つ作って動かせる / Actions タブでログを読める / 手動実行できる
2. **前提** — GitHub の public リポジトリがあり、`gh` CLI が認証済みであること
3. **なぜ必要か** — 「push したら自動で何かが動く」を最初に体感しないと、以降のすべてが抽象論になる
4. **手順** — Step 1〜4 の内容を、Actions タブのスクリーン操作込みで書く
5. **何が変わったか** — 以下の用語を、`hello.yml` の該当行を指しながら定義する
   - **イベント**（`on:`）→ **ワークフロー**（ファイル1つ）→ **ジョブ**（`jobs:` の子。並列に走る）→ **ステップ**（`steps:` の子。上から順に走る）
   - **ランナー**（`runs-on:`）は GitHub が用意する使い捨ての仮想マシン。ジョブごとに新品が割り当てられる
   - `run:` はランナーのシェルでコマンドを実行する。`uses:` は他人が作った処理を呼ぶ（Stage 1 で使う）
   - `needs:` はジョブの実行順序を作る。書かなければジョブは並列に走る
6. **つまずきポイント** — 以下を症状つきで書く
   - `ls -la` にリポジトリのファイルが無い → ランナーは空。`actions/checkout` が必要（Stage 1 で解決）
   - YAML のインデントをタブでずらすと `You have an error in your yaml syntax` になる。**タブは使えない。半角スペースのみ**
   - ワークフローファイルが `.github/workflows/` 直下にないと、そもそも Actions タブに現れない
   - `workflow_dispatch` を追加しても、**そのワークフローがデフォルトブランチに存在しないと**手動実行ボタンが出ない
7. **演習課題** — 下記 Step 6 の 3 問
8. **実務への持ち込みメモ** — ジョブ間でファイルを渡したいときはランナーが別物なので artifact か job outputs が要る（Stage 3・4 で扱う）。この制約を知らずに「なぜかファイルが消える」と悩む人は多い

- [ ] **Step 6: 演習課題と解答を書く**

`docs/stages/answers/stage-00.md` に、以下 3 問と解答（動く YAML 断片）を書く。

- **問1**: `greet` ジョブに「現在の GitHub リポジトリ名を表示するステップ」を足す。
  解答: `run: echo "$GITHUB_REPOSITORY"`（`GITHUB_*` 環境変数はランナーに自動で入っている）
- **問2**: `check-isolation` を `needs: greet` 無しにすると何が起きるか予想し、実際に外して確かめる。
  解答: 2 つのジョブが同時に走る。ログのタイムスタンプが重なることで確認できる。`needs` は依存関係であって単なる順序指定ではない
- **問3**: わざとステップを失敗させ（`run: exit 1`）、後続ステップが実行されないことと、
  ジョブ全体が赤くなることを確認する。
  解答: 既定ではステップが失敗した時点でジョブは中断する。続けたい場合は `continue-on-error: true`（Stage 4 で扱う）

```python
"""売上レコードの読み取りと月次集計。

このモジュールは副作用を持たない純粋関数だけで構成する。
CLI・API・GUI・Databricks は、すべてここを薄く包むだけにする。
"""

from __future__ import annotations

from collections import defaultdict
from collections.abc import Iterable, Mapping
from dataclasses import dataclass
from datetime import date
from decimal import Decimal, InvalidOperation

REQUIRED_COLUMNS = ("date", "product", "quantity", "unit_price")
HEADER_LINE_COUNT = 1
NO_DATA_MESSAGE = "(対象データなし)"


@dataclass(frozen=True)
class SalesRecord:
    """CSV の 1 行に対応する売上レコード。"""

    sold_on: date
    product: str
    quantity: int
    unit_price: Decimal

    @property
    def amount(self) -> Decimal:
        return self.unit_price * self.quantity


@dataclass(frozen=True)
class MonthlyTotal:
    """ある月の集計結果。month は "2026-01" 形式。"""

    month: str
    total_amount: Decimal
    record_count: int


def parse_records(rows: Iterable[Mapping[str, str]]) -> tuple[SalesRecord, ...]:
    """文字列の辞書列を SalesRecord に変換する。不正な行があれば ValueError。"""
    return tuple(
        _parse_row(row, line_number)
        for line_number, row in enumerate(rows, start=HEADER_LINE_COUNT + 1)
    )


def _parse_row(row: Mapping[str, str], line_number: int) -> SalesRecord:
    missing = [column for column in REQUIRED_COLUMNS if column not in row]
    if missing:
        raise ValueError(f"{line_number}行目: 列が足りません: {', '.join(missing)}")

    try:
        return SalesRecord(
            sold_on=date.fromisoformat(row["date"]),
            product=row["product"],
            quantity=int(row["quantity"]),
            unit_price=Decimal(row["unit_price"]),
        )
    except (ValueError, InvalidOperation) as error:
        raise ValueError(f"{line_number}行目: 値を解釈できません: {error}") from error


def aggregate_monthly(records: Iterable[SalesRecord]) -> tuple[MonthlyTotal, ...]:
    """月ごとの売上金額と件数を集計する。結果は月の昇順。"""
    amounts: dict[str, Decimal] = defaultdict(Decimal)
    counts: dict[str, int] = defaultdict(int)

    for record in records:
        month = f"{record.sold_on:%Y-%m}"
        amounts[month] += record.amount
        counts[month] += 1

    return tuple(
        MonthlyTotal(month=month, total_amount=amounts[month], record_count=counts[month])
        for month in sorted(amounts)
    )


def format_table(totals: Iterable[MonthlyTotal]) -> str:
    """集計結果を人間が読める表に整形する。"""
    header = ["月       件数         売上金額", "-------- ---- ----------------"]
    body = [
        f"{total.month} {total.record_count:>4} {total.total_amount:>16,}" for total in totals
    ]
    return "\n".join(header + (body or [NO_DATA_MESSAGE]))
```

   - `pull_request` に `paths` フィルタを付けて必須チェックにすると、PR が永久に待ち状態になる（本ステージで `push` 側にだけフィルタを付けた理由）
   - 必須チェックはジョブの **`name:`** で指定する。`jobs:` のキー名ではない。`name` を変えると必須チェックの設定が外れ、**ゲートが無言で無効化される**
   - `concurrency` で古い実行がキャンセルされるのは正常。赤ではなく灰色の `cancelled` になる
   - ruleset は**自分自身にも適用される**。管理者もバイパスできない設定にすると、緊急時に困ることがある
7. **演習課題** — 下記 Step 12 の 3 問
8. **実務への持ち込みメモ** — 既存リポジトリに必須チェックを入れるときは、まず Enforcement status を **Evaluate**（記録するだけ）で数日運用し、既存の PR フローを壊さないか見てから Active にする

- [ ] **Step 12: 演習課題と解答を書く**

`docs/stages/answers/stage-02.md` に 3 問と解答を書く。

- **問1**: `docs/` だけを変更した PR を作り、CI が走ることを確認する。なぜ `pull_request` 側には `paths-ignore` を付けていないのか説明する。
  解答: 必須チェックにしているため。スキップされたチェックは「成功」ではなく「未報告」になり、PR がマージ不能になる
- **問2**: `concurrency` の `group` から `${{ github.ref }}` を消すと何が起きるか予想し、確かめる。
  解答: 全ブランチの実行が同一グループになり、他人の PR の CI が自分の push でキャンセルされる。`group` にはブランチを含める
- **問3**: `ci.yml` のジョブの `name:` を `Lint and Test` に変更して PR を出す。
  解答: 必須チェック `Lint & Test` が報告されなくなり、PR がマージできなくなる。
  ジョブ名は必須チェックの識別子でもあるため、安易に変えてはいけない。確認後は元に戻す
